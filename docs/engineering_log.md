# Day 1（2026-10-02）：从一句话需求到 v1.1.0 完整后端版

## 一、今日目标与图纸设计（人类输入）

### 需求描述

原始需求只有一句话：

> 「帮我开发一个拼豆图纸生成网站：用户上传图片，自动转成拼豆图纸。」

人类在开发前把它逼成了一组可验收的硬指标，依据是拼豆的真实使用场景：玩家要**照着格子一颗一颗放豆子**（图纸必须能数格子）、**按颜色备料**（必须有用量统计）、**大图纸要分块拼**（必须有分区编号）。

### 实际架构选定（人类决策）

开发前锁定了四个「选错就全部返工」的关键点，全部由人类拍板：

1. **色卡体系 → 多品牌可切换**：内置 4 个品牌色卡（Artkal 64 色 / COCO 可卡 60 色 / 漫漫 56 色 / Perler 42 色），支持用户上传自定义色卡（JSON/CSV）。色值是公开资料近似值，页面明示免责。
2. **网格尺寸 → 预设档位（29/48/58/96）+ 滑块自定义**，每边 10~200 颗（后按实测性能放宽到 400）。
3. **技术栈 → FastAPI 后端 + 原生前端**。人类评估过三个方案后拍板：

   | 方案 | 结论 |
   |---|---|
   | 纯前端单页 | 零成本但数值计算在 JS 里吃力 |
   | **FastAPI + 原生前端（采纳）** | 量化算法用 Python + numpy 写得干净又快；前端零构建零 CDN，无供应链风险 |
   | 后端 + 大型前端框架 | **否决** —— 引入构建工具链对这个体量是过度设计 |

4. **图纸输出四项全要**：坐标轴网格、格内色号（格子边长 ≥14px 才写，避免糊成一团）、10×10 分区编号、导出可打印 PNG。

接口契约同样先于代码定死：`/api/generate` 的请求字段、响应结构（`grid` 是二维数组，外层行内层列，元素是色号或 `null`）、7 个错误码（中文报错）。事后证明这让测试专家能完全脱离前端直接对着契约生成断言。

### 任务拆分

三角色 AI 团队分工，**职责不交叉**：交付总监（拆需求、定契约、编排、汇总）不写代码；全栈工程师（实现）不做验收判断；质量工程师（验证）不改代码。跨成员的信息流一律经交付总监中转，任务描述必须自包含。

## 二、AI 执行过程与干预（管理动作）

### 执行情况

| 阶段 | 负责 | 耗时（有计时记录） |
|---|---|---|

产出：14 个文件共 3213 行。实现者自检 31 项接口测试 + headless Chrome 驱动真实页面 21 项断言，全部通过。

### 人类干预（不是自己写代码，而是把现象/日志交给 AI 并修正指令）

Day 1 深夜到 Day 2 凌晨，人类以「验收者」身份连续报出真实缺陷，交付总监先诊断根因再派活：

- **「页面转圈不消失」**（v1.0.1）：人类反馈现象，AI 定位修复，配 51 项独立回归。
- **「色块分辨模糊、放大看不到分区编码」**（v1.0.2）：第一步不是改代码，而是先做定量诊断实验把「还原度低」量化，确认根因层次后修复，配 41 项独立回归。
- **「抖动产生杂色」**（v1.0.4）：用四组对照实验——每次只改色度误差这一个变量，其余保持不变——钉死根因：误差向量的色度分量在扩散过程中把灰格「传染」出紫/蓝/粉异色点。方案是按源像素饱和度自适应衰减色度误差（实验对照图见本仓库 `assets/07`、`assets/08`，修复前后对比见 `assets/02`、`assets/03`）。配 46 项独立验证。
- **「网格能不能更大」**（v1.0.5）：先做前后端性能实测（200~600 六档）再放宽上限 200→400，用数据代替拍脑袋。
- 并发与安全加固（v1.0.6 / v1.0.7）：修掉 `async def` 里做同步 CPU 计算拖死整个服务的并发缺陷，补单次生成限流与解压炸弹防护。

**编排层的两个关键动作**（证明交付总监不只是转发任务）：

1. 环境障碍不等成员报错，提前把 pip 被代理拦截的问题解决掉；
2. **指定怀疑清单**：交付总监读完成员代码后，点名四个最可能出问题的点（占比求和偏差、alpha 阈值、抖动是否真生效、最坏性能组合）作为必测项派给测试专家，而不是泛泛地说「帮我测一下」。

> 注：Day 1 各修复轮次的具体时刻未逐条记录（Git 首个提交在次日 01:00，是补建的基线）。轮次与版本号以原项目 `ENGINEERING_LOG.md` 第 12~18 节为准。

## 三、测试与验收（人类验收 + 独立验证）

### 测试用例设计

- 实现者自检：31 项接口测试 + 21 项真实浏览器断言；
- 独立验证：质量工程师**不复用**实现者的测试，自建 77 项边界/异常用例，并交叉跑那 31 项 —— 结果 76 过 1「失败」，复核确认那 1 项是测试自己断言的比较式写反了，产品侧无缺陷。

关键验证数据（全部实测，出自原项目 `ENGINEERING_LOG.md` 第 8.2 节）：

| 检查项 | 结果 |
|---|---|
| width/height 边界：9 / 201 / 0 / -5 / abc | 全部 400 INVALID_PARAM |
| 文件恰好 10MB / +1 字节 | 放行后解码失败 400 / 413 TOO_LARGE |
| alpha 阈值边界 | 0→0 颗、127→0 颗、128→400 颗、255→400 颗，**确认 128** |
| percent 求和（12 组，含 64/64 全用色压测） | 精确 100.000000（最大余数法） |
| 抖动真生效 | dither on/off 的 grid hash 不同 |
| 10 线程并发同输入 | 10/10 返回 200，hash 完全相同（无串数据） |
| 自定义色卡 8 种非法输入 | 8/8 返回 400，无 500 |
| 性能：200×200 无抖动 / 最坏组合（抖动+限色64） | 118ms / 1186ms，无性能悬崖 |

### 黑盒测试发现的问题

- **全透明图**返回空图纸（`totalBeads=0`）、**多帧 GIF** 静默取第一帧 —— 确认为合理行为边界，记录在案而非修复；
- 「极端长条图锁定等比时比例丢失但不越界」同上。

### 修复验收

每轮修复由交付总监定位根因 → 全栈工程师修复 → 质量工程师独立回归 → **人类亲自上手复验**。人类验收动作贯穿全程，v1.1.0（使用统计 / 反馈 / 周报）按人类定的边界收尾：反垃圾要「去重 + 防恶意 + 拦涉黄广告」、报告按频次排序、周报每周一次发到指定邮箱。

## 四、Token 成本与效能分析

本项目未接入 Token 计量，精确消耗**未统计**，仅给结构性结论（推法见 [token_cost_report.md](token_cost_report.md)）：

- 最烧 Token 的动作是**缺陷修复回环**：每轮要把现象、根因分析、相关代码上下文重新装载一次；
- 已实施的省法：子任务**自包含**下发（避免跨成员传递完整历史）、滑动窗口式上下文管理、差分测试期望值由 Python 生成（省掉人工对答案的来回）。

**瓶颈在哪里，从时间分布就能看出来。** AI 侧的单轮 v1.0 开发耗时 19 分 29 秒、独立验证 3 分 42 秒，而「约 11 小时」中的绝大部分，花在了需求拆解、缺陷诊断、部署排查和人类验收上。这不是效率问题，而是这套模式的设计意图：**人是质控点，不是用来绕开生产瓶颈的捷径**——把 AI 的生成速度再翻倍，也不会省掉「逐行对照真身」「部署完再验一次」「把现象读成根因」这些必须人来判断的动作。

# Day 2（2026-10-03）：静态化、上线与 Functions + D1 收尾

## 一、今日目标与图纸设计（人类输入）

### 需求描述

Day 2 的目标是把 v1.1.0 的完整后端版**变成 0 元可运营的线上站**。人类给出三个决策：

1. **拍板「零构建、零 CDN、纯静态」路线**（理由：零成本、好部署、图片不出本机）—— 把「生成」与「色卡」搬进浏览器，后端从「必需」降级为「增值」；
2. **拍板「先上线、打不开不管，要的是完整性」**（`*.pages.dev` 在境内的可达性不由代码控制）；
3. **拍板放弃百度收录**（判断理由：主域名不是自己的，只是依附的子域名）；改走 IndexNow（必应/Yandex 即时收录协议，零成本）。

### 实际架构选定

纯静态形态下五个后端依赖的处置：`/api/generate` 改由浏览器内 `engine.js` 计算；`/api/palettes` 改为静态 `palettes.js`（**由脚本从后端 JSON 生成，不手抄**——色卡是唯一事实来源，手抄等于制造两份真相）；统计与反馈「有后端就走接口，没有就静默降级」（反馈降级为调起邮件客户端）。关键设计是**不写两套代码**：前端探测 `/api/health`，同一份前端在两个形态下跑同一套渲染代码。

### 任务拆分

静态化 → 部署 → 收录推送 → 把使用统计与反馈接回后端（v1.3.0），四个子任务依次下发。

`engine.js` 是 `backend/quantize.py` 的浏览器版复刻（731 行），对齐的是实现细节而非「看起来差不多」：复刻 Pillow 定点整数重采样、两趟间 clip8 回 8bit、规避 JS 银行家舍入差异。一致性证据：`verify_parity.js` **17/17，20850 格逐格完全一致，最大色差 ΔE = 0.0**。

量化进 Web Worker 前先 A/B 实测：主线程心跳最大间隔 499ms（有 Worker）vs 632ms（无），差值约 133ms 是量化占住主线程的时间 —— **先量再做，量完敢改结论**：原先估的「省 4 秒」是 Python 后端的耗时，JS 引擎快得多；真正受益的是手机端。

### 人类干预

**改 Prompt 而不是改代码的典型场面：**

1. **子代理自称「103 项差分全绿」，交付总监逐行对 Python 真身，发现两个缺口**：缺「生成次数」上报（visits 表只能回答「来了多少人」，答不了「用了多少次」）；反馈接口少了一道必须在校验之前执行的粗限流。→ 派回补齐，语义照抄 Python 版。
2. **手写期望值错了 3 条**（其中一条是「两个链接应放行」，Python 判的是涉黄广告拦截 —— 两个模式各匹配 2 次共 4 个匹配）。→ 改为期望值一律由 `.tooling/_py_expect_fb.py` 从 Python 真身生成，JS 照着比。教训：手写期望值等于把「我以为对」固化成断言，测试会替错误背书。

**从 PASS 的测试输出里肉眼读出的 bug：**

- `meta.sourceSize` 变成 `undefinedxundefined` —— 这个 bug **没有任何一条断言覆盖**：测试全绿，只是在 PASS 的 detail 里肉眼读出了「原图 undefinedxundefined」。根因：原图尺寸只有解码后才知道，`buildBody()` 读的是点击那一刻的参数快照，解码结果没回写。教训：测试全绿也要读 detail；断言要写「等于什么」，不能只写「包含什么」。

**部署四坑 —— 每个都是命令行显示成功、实际静默失败**（v1.3.0）：

| # | 现象 | 根因 |
|---|---|---|
| 1 | `d1 create` 报 Authentication error | 令牌只有 Pages:Edit 没有 D1 权限；细分令牌权限不能事后改，只能重建 |
| 2 | Functions 一个都没上去，`/api/health` 404 | `functions/` 放错目录，wrangler 只认配置文件所在目录下的 `functions/` |
| 3 | D1 绑定被整体忽略 | 配置缺 `pages_build_output_dir` 字段时 wrangler 打一行警告就忽略整个配置文件 |
| 4 | `wrangler.toml` 被传上公网（内含数据库绑定 ID 等配置） | `pages deploy` 会把输出目录整个上传，配置文件也不例外 |

对应修正：配置放项目根、账号 ID 走环境变量（不写进配置文件）、**每次部署完必须 `curl /api/health`，不能只看命令行**。第 4 坑修完确认线上已 404（当时刷到 200 是 CDN 未过期的旧缓存）。

**「数据搬了家但没人通知读数据的人」**（v1.3.0 连带问题）：数据进 D1 后，周报还在读本地 SQLite —— 不打通的话，每周一发的周报会永远「看着像没人用」。修法选同步（`sync_d1_to_local.py`，两库表结构逐字一致，搬回报表零改动），实测幂等：连跑两次第二次新增 0 条。同时删掉了撞车的重复周报自动化（两条都定在周一 09:00，会发两封一样的）。

**导出完成 ≠ 交付**（人类原话「保存的图片去哪里了 我要验收」）：进度条停在 100% 但没有任何东西落到用户手上。按设备分两条路修 —— 电脑自动触发下载；手机给出「长按图片 → 存到相册」的明确指引。判据用指针媒体查询而非屏幕宽度，有实测依据：CDP 只调窄宽度时指针仍是 `fine`，平板横过来宽度像电脑但依然是触屏。

## 附二：一条未修复、但说清楚了原因的遗留问题

刻意保留这一条，是为了说明这套交付模式对「完成」的定义：**已修的要有证据，未修的要有结论。**

**Artkal 色卡的中性色数量不足。** 该色卡只有 8 个中性色，亮度轴上存在 24.1 的空洞。关闭抖动时，中性区仍有约 0.2% 的染色残留（约 8 格 / 4200 格），表现为画面中性处零星几个偏色的格子。

**为什么不修**：这是**色卡数据本身的灰阶不足**，不是算法缺陷。唯一的解法是补充 Artkal 官方真实色值，但项目使用的是社区整理的公开参考数据（见 README 免责声明），没有官方数据源，因此无法在算法侧解决。

**对应做法**：把它如实写进文档，而不是改成「看起来正常」的输出。同类情况（如分区角标遮挡首格色号、深浅交界细线在浅色侧不可见）在原项目日志中也都按「判定可接受 / 判定数据限制」分开记录，不做含混处理。

> 以上数字出处：原项目 `ENGINEERING_LOG.md` 第 15.8 节「遗留局限（非本次修复引入）」。
