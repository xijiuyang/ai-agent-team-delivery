# Token 成本报告

> ⚠️ **数据口径声明（先读这一段）**
> 本项目**未在项目侧接入任何 Token 计量**：AI 团队的会话没有逐次统计输入/输出 Token 数，也没有留存可汇总的原始账单。因此本文**不提供项目侧的精确 Token 消耗数字**。
>
> 但有一个例外：**平台侧存在积分（Credits）计量**，这是一个粗粒度的真实数据（见 §0）。它能给出「总量」和「时间跨度」，但**无法拆分到阶段、任务或成员**。
>
> 以下内容分三类：
> - **§0 平台积分数据** —— 真实观测值（总量口径），但换算为 Token 需要平台汇率，而公开汇率分歧达 7.8 倍，故只给区间不给单值；
> - **结构性结论**（成本构成、已实施的优化手段）—— 基于真实的协作机制与过程记录，可靠；
> - **估算部分** —— 均明确标注「估算」并写出估算方法，可信度低于实测。

## 1. 成本构成拆解（结构性结论，非计量数据）

按「哪类动作最烧 Token」排序（估算，方法见 §4）：

| 排序 | 动作类型 | 为什么烧 | 相对量级（估算） |
|---|---|---|---|
| 1 | **缺陷修复回环** | 每轮要把缺陷现象、根因分析、相关代码段、上一轮的修复尝试重新装载进上下文；修复后还要为回归测试再装载一次 | 高 |
| 2 | **独立验证** | 测试专家要读实现产出原文 + 验收标准 + 相关代码，再自建全套用例；13 套测试套件的编写与执行本身是大体量输出 | 高 |
| 3 | **自包含子任务下发** | 上下文隔离的代价：每个子任务必须携带完整的背景（需求、契约、约束、验收标准），相同背景在多个成员处各装载一次 | 中 |
| 4 | **架构决策与契约设计** | 一次性投入，但它决定了后续不需要返工 —— 是「省 Token 的花销」 | 中 |
| 5 | **常规代码生成** | 有清晰契约和任务拆分后，反而不是大头 | 低 |

结构性结论：**这个交付模式里最贵的不是「写代码」，而是「对齐认知」**——把现象变成根因、把需求变成契约、把验收标准变成断言。这与「人类做决策 + AI 执行」的设计互为因果：人类干预的质量（是否一次说清、是否给出现象而非情绪）直接决定回环次数，也就直接决定成本。

## 2. 已实施的优化手段（真实措施，可追溯）

以下手段在项目中真实实施，效果方向明确（具体省了多少未统计）：

1. **子任务自包含下发**：成员之间看不到彼此的对话，跨成员信息流经交付总监中转，任务描述必须自带全部背景。代价是每个任务都重复携带背景；收益是每个成员的上下文只装自己那一段，不会被整条历史撑爆。
2. **滑动窗口式的上下文管理**：长会话（如连续多轮缺陷修复）只保留当前窗口需要的代码段与结论，过期轮次被挤出窗口，而不是无限累积。
3. **差分测试的期望值由 Python 真身生成**（`.tooling/_py_expect_fb.py`、`.tooling/_py_expect_gen.py`）：避免人工推演期望值 → 测试挂掉 → 人工再对答案的多轮来回；实际上第一次手写期望值就错了 3 条，每条都是一轮回环。
4. **接口契约前置**：`/api/generate` 的字段、结构、错误码在写代码前定死，前后端并行推进而不对不上 —— 省掉的是最贵的一类返工（前后端对齐）。
5. **「先量再做」**：优化前先实测（如 Web Worker 收益 A/B 实测：主线程心跳 499ms vs 632ms），避免在错误的方向上消耗整轮实现 + 验证 + 回滚的成本。

## 3. 「如何取得真实值」（给后来者的操作指引）

如果要在同类项目中拿到精确 Token 数据，建议在团队机制里加一层计量：

1. **API 侧计量**：所有模型调用走统一网关/代理，在网关记录每次请求的 `prompt_tokens` / `completion_tokens` / 模型名 / 时间戳 / 关联任务 ID，落库；
2. **任务级归集**：给每个子任务分配唯一 ID，成员产出的每次调用都带上该 ID，即可按「任务 → 阶段 → 全项目」三层汇总；
3. **区分动作类型**：在网关侧打上动作标签（生成 / 测试 / 诊断 / 修复回环），这样 §1 的构成表就能从「估算」升级为实测；
4. **对比基线**：同时记录「人类单独开发等价功能」的对照数据（如代码评审工时、调试工时），否则只有 Token 数没有意义 —— 成本的正确单位是「每通过一项验收的 Token」，不是「每次对话的 Token」。

## 4. 估算方法说明

§1 的相对量级排序是估算，方法：

- 依据协作机制推演：每次「回环」至少包含「现象描述装载 + 代码上下文装载 + 修复输出 + 回归验证」四次大体量装载，而一次常规代码生成只有「任务装载 + 代码输出」两次；
- 依据过程记录交叉验证：原项目 `ENGINEERING_LOG.md` 记录的耗时分布（开发 19 分 29 秒 / 独立验证 3 分 42 秒，而缺陷修复与部署排查持续数小时）与「修复回环 > 常规生成」的排序一致；
- **但请注意**：耗时占比 ≠ Token 占比，排序未经过计量验证，仅用于说明成本结构的大致形状。
