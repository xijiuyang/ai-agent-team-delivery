# 拼豆图纸生成器 · 测试用例集与质量证据

> 写这份文档的目的不是「罗列用例」，而是回答一个问题：
> **AI 写出来的代码，人类是怎么把它验到能用的？**
>
> 所以每一节的排布都遵循同一条顺序：**先把约束和边界列出来 → 再按边界设计用例 → 最后如实记录哪些是真被测出来的、哪些不是。**
>
> **硬约束**：本文档每一个数字、每一条用例，都能在 `pindou-studio` 的真实测试脚本或源码里找到出处；查不到的明确标「未覆盖」，**不为凑数编造**。
>
> **阅读约定**
> - 「结论」列四种取值：
>   - `✅ 已覆盖` —— 断言真实存在于对应测试文件，改坏了会报警
>   - `🔍 本次实测确认` —— **仓库没有这条断言**，是编写本文档时实测确认的行为；**改坏了不会报警**，风险高于 ✅
>   - `⚠️ 部分覆盖` —— 只有单侧或间接覆盖，缺关键一侧
>   - `❌ 未覆盖` —— 既无断言，本次也未能实测
> - 「实际」列标 `实跑` 的是编写本文档时真实执行验证过的；标 `仓库记录` 的是脚本里存在该断言、仓库记录为通过，但本轮未重新执行（原因见最后一节）。
> - **本文档不含任何令牌、邮箱地址、数据库 ID、账号 ID、真实 IP。** 举例一律用脱敏写法。

## 2. 测试策略

1. **验证者独立性**：质量工程师拿到的是「产出原文 + 验收标准」，不复用实现者写的测试就下结论——复用等于让实现者给自己判卷。
2. **形态分离**：同一产品两种运行形态（纯静态 / Functions+D1）分开测。`check_static.js` 跑在一个刻意把 `/api/*` 全部返回 404、且带与线上一致 CSP 的模拟服务上——让「测出来能用」尽量接近「上线后真能用」。
3. **差分测试**：JS 侧期望值一律由 Python 真身生成（`_py_expect_*.py` → `_expect_*.json`），不手写。手写期望值曾一次错 3 条。
4. **怀疑清单**：交付总监读码后点名必测的高危点（占比求和偏差、alpha 阈值、抖动是否真生效、最坏性能组合）。
5. **部署后独立验证**：每次部署完必须 `curl /api/health` + 端到端回归，**「命令行显示成功」不算数**。

### 5.1 B-25 专项：联系方式截断会静默破坏邮箱

实测（临时库，`normalize_contact` + `feedback_problem`）：

| 输入长度 | 截断后 | 截断结果尾部 | 校验码 |
|---|---|---|---|
| 120 | 120 | `cc@example.com`（完整） | `''` 放行 |
| 121 | 120 | `ccc@example.co`（**被切掉 1 个字符**） | `''` **仍然放行** |
| 125 | 120 | `ccccccc@exampl`（TLD 都没了） | `BAD_CONTACT`「邮箱格式看起来不对，检查一下，或者留空也行」 |

**结论**：121~124 字符这个区间，邮箱会被静默截断成一个**错误的地址并通过校验**，用户完全不知情；125 字符以上才报错，但报错说的是「格式不对」——用户更难想到真实原因是「太长了」。

这是一个**真实缺陷**（静默数据损坏 + 提示指向错误方向），且**仓库里零断言覆盖**。修法建议：超长时直接拒绝并明确说「联系方式最多 120 字符」，而不是截断后去校验残骸。

### 5.2 构造边界用例时的两个坑（比边界值本身更常踩）

1. **用重复字符构造长文本，测不出长度边界**。构造「500 字放行用例」时，用「测」字重复 500 次命中的是 `SPAM`（同一字符连续 4 次以上的规则），而不是放行。改用无连续重复字符的文本才拿到干净的 499 / 500 / 501 三档。
2. **判重类用例会互相污染**。第一次测 B-27 时，我把 47h 和 49h 两条历史数据用了同一段正文，结果 49h 那次也被判 `DUPLICATE`——因为全站去重查的是「是否存在该 `content_key` 的近期记录」，47h 那条还在窗口内，把 49h 的用例污染了。**判重测试每条用例必须用不同的正文、不同的设备。**

## 11. 测试自身的 Bug（假失败）

> 测试报错 ≠ 产品坏了。下面四个案例里，A、B 是「测试自己写错了」，C 是「阈值口径定错了」，D 是我这次写文档时自己犯的。

### 案例 A：ZIP 超时——测试脚本点错了按钮

`check_tiles_export.js` 第一版直接等 zip 落盘，必然超时。注入钩子后确诊：**「导出图纸」按钮只负责把图画出来并展示，真正的下载是另一个按钮（打包按钮）**。产品没坏，是脚本按错了按钮。

- 教训：**断言之前先确认被点的是不是那个按钮**。UI 自动化里的「超时」往往不是性能问题，是流程理解错了。

### 案例 B：`sourceSize`——测试全绿，但值是 `undefined`

反过来的一课。这个 bug **没有任何一条断言覆盖**：测试全绿，只是 PASS 的 detail 里写着「原图 undefinedxundefined」，是**肉眼读出来的**。

- 教训一：**断言要写「值等于什么」，不能只写「包含某个子串」**——值变成 `undefined` 时，子串断言照样过。
- 教训二：**测试即便全绿，也要读一遍它的 detail 输出。** 全绿不等于没问题。

### 案例 C：断言口径写死导致误报

早期自建脚本把占比断言写成 `=== '100%'`，而接口实际返回 `100.00%`（最大余数法保证精确两位小数），一次误报 FAIL，改为数值容差比较后才全过。同类还有两处：

- 缩略图体积阈值原来卡「单张 < 60KB」，但缩略图大小取决于图有多花（色彩丰富的照片单张就能到 62KB），阈值一紧就假失败——真正影响页面的是**总量**，改成「单张 < 200KB 且全部 < 1MB」。
- 判断「走不走分块」不能用「网格 ≥ 300 就一定是分块」这种猜测，必须读页面实际选中的模式——一张色彩丰富的照片在 120 格时同样会被判成分块，**猜就会假失败**。

- 教训：**阈值型断言要卡在真正影响体验的那个量上**，而不是随手取一个看着合理的数。

### 案例 D：我的判重探针污染了自己

这次实测 B-27（48 小时判重窗口）时，我把「47 小时前」和「49 小时前」两条历史数据用了**同一段正文**。结果 49 小时那次也被判 `DUPLICATE`——因为全站去重查的是「该 `content_key` 在窗口内有没有记录」，47 小时那条还在窗口里，把 49 小时的用例污染了。

第一反应差点写成「判重窗口失效，48 小时形同虚设」。改用不同正文、不同设备重跑后确认：**47h → DUPLICATE、49h → 放行，逻辑是对的。**

- 教训：**用例之间必须互相独立**。判重、限频、去重这类「依赖历史状态」的用例，每条都要用独立的正文 / 设备 / IP，否则会得出「产品有 bug」的错误结论——而产品其实是好的。这跟案例 A 是同一类错误的两面：A 是「产品好但测试报错」，D 是「产品好但测试让我以为它坏」。

### 14.1 一处归因更正（我自己的更正）

上一版核对中，我曾判定「`width=9 / 201 / 0 / -5 / abc`、空文件、10MB+1 字节、截断 PNG、`maxColors=1/65`、CMYK JPEG、多帧 GIF」这批用例是编造的，理由是它们在 `tests/test_api.py` 里 0 命中。

- **但它们是人工验证记录，不是自动化断言**——也就是说这批边界**没有回归保护**，改坏了不会报警。这恰恰是我把它们标为「未覆盖」的正确理由，只是理由应该写成「有人工验证记录、无自动化断言」，而不是「不存在」。
